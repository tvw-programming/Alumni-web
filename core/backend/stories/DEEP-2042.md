## Description

Users have no way to get a copy of the data we hold about them. Support
currently answers these requests by hand, and the privacy policy we published
last quarter promises self-service export.

A signed-in user should be able to request an export of their own profile from
the users API and receive it as JSON. The export is theirs alone: nobody may
export another person's profile.

The file is written through `app/services/storage.py`, which already writes to
a local directory in development and to object storage in production. Reuse it
rather than adding a second storage path. The route belongs in
`app/api/users.py` under the existing `/api/v1/users` prefix, and authorisation
uses `subject_id` from `app/deps.py`, the same way the display-name route does.

## Acceptance Criteria

- AC-1 An authenticated user can export their own profile via GET /api/v1/users/{user_id}/export
- AC-2 The export contains exactly id, display_name, email, avatar_url and created_at
- AC-3 A request for another user's export is refused with 403 and writes nothing
- AC-4 An export for an unknown user id returns 404
- AC-5 The export file is written through app/services/storage.py, not a new storage path

## Out of scope

- CSV or PDF export formats
- Asynchronous or emailed exports
- Order history, audit logs, or any data outside the user profile
- Rate limiting and export quotas
- Deleting or expiring previously generated export files

## Notes

The response returns the JSON body directly; the stored file exists so support
can re-send the same export without regenerating it.

`created_at` is a datetime on the `User` model but is not currently exposed by
`UserProfile`. The export is the first place it becomes visible, which is
intended — it is the user's own data.
